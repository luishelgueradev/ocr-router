## The two defects that were not on the list

**Wall-clock deadlines.** The suite was not the "352/352 green" the phase record
claimed — it failed 2 of 6 runs. Instrumenting the failure produced:

```
DBG-FAIL stopped_reason=passed elapsed=-791
DBG-attempts=[{"engine":"ocrspace-engine2","time_ms":-791,...}]
```

A negative elapsed: the wall clock stepped ~1.1s backward mid-run, `remaining`
inflated past `minSliceMs`, and the runner escalated to a tier the budget had
already spent. Not a flaky test — the single authoritative job deadline
(`worker.js`, `deadline = Date.now() + MAX_JOB_MS`) rested on the same
arithmetic, so on a VPS running NTP a forward step kills jobs that still had
budget and a backward step lets them run past `MAX_JOB_MS`. Fixed by moving all
elapsed/deadline arithmetic to `lib/clock.js` `monotonicMs()`; `expires_at`
stays on the wall clock through an explicit `wallMs()` seam, because it is an
absolute timestamp a client compares against civil time.

**Cross-process temp-dir deletion.** A second intermittent failure — a directory
deleted between its own `mkdtemp` and the very next write. `temp.js`'s WR-10
orphan sweep removes every `ocr-job-*` dir under `os.tmpdir()` not owned by the
current process, and documents the precondition "single-instance per container".
Production honours it; `node --test` does not, since it runs each test file in a
parallel process sharing the host `/tmp`. Instrumentation confirmed
`test/temp.test.js` deleting dirs it did not own on every suite run. Fixed on the
test side (private `TMPDIR` per process); the sweep is deliberately unchanged.

## Not vacuous, and one thing the suite caught

The monotonic migration introduced a real bug that only running the tests found:
`AbortSignal.timeout()` rejects a non-integer delay, and a monotonic reading is
fractional, so the per-engine slice had to be floored. Reading the diff would not
have surfaced it.
